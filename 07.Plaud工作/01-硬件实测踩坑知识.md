# 硬件实测踩坑知识（SIGMA 治具）

> 全部来自真机实测（2026-07-15 ~ 2026-07-23），是整个项目里复盘价值最高、也最容易随时间/人员流失的知识。方法论沉淀见 [[02-Skill沉淀清单]] 的 sigma-hardware-attribution / sigma-log-anchor-debugging。

## 实验室物理接线（2026-07-15 起，多次改线更正）

- **COM3**：盒子 USB CDC 日志口，波特率 230400。
- **继电器板通道映射**（板面标号与实际接线**相反或错位**，这是整个归因过程反复踩的坑）：
  - 最终闭环对应表（2026-07-17 14:30 复验）：**R8=左耳红外、R9=右耳红外、R10=左耳压感、R11=右耳压感**。
  - COM16/COM17 为按键/开关盖/Pogopin 继电器板；COM18 为红外/压感板，**不支持反馈协议**（动作正常但不回帧，config 走 `feedback: false`）。
- **UART 抓包口角色**（以 `config.py` 为准，早期因 DebugAnalyzer 信道分配混乱导致过一整天的侧别推断错误）：**COM15=左耳、COM13=右耳、COM14=盒子**，2000000 波特率。COM13 有停流前科，用例前先查文件字节数是否在涨。

**教训**：新板/改线后，所有历史侧别结论作废，必须逐路扫描 + 认固件日志锚点（KEY 日志、`Force IRQ`、`hx300x_int_gpio_intr_cb`）重新标定，不认接线图或板面标号。

## 归因方法论（继电器动作了但固件没反应，怎么查）

根因从来不是单一层，按下面顺序排查：

1. **先进稳态再施激励**：依赖蓝牙连接的实验必须等重连完成（开盖后约 11 秒）；佩戴/出入耳前置=先开盖再出盒（关盖时固件不刷新耳机在位状态，读数是陈旧值）。
2. **单变量**：每次只动一路，短沿/长保持分开试，吸合沿和断开沿语义可能不同（如压感 INT 低有效仅吸合沿触发）。
3. **逐层验证根因链**：INT 边沿到达 ≠ 芯片判定 ≠ 状态机动作，逐层找日志锚点定位断在哪一层。
4. **与真人操作对照**：真人全链路通、继电器断在哪层，那层就是给固件的精确需求描述。
5. **排除环境屏蔽**：先确认没有更高优先级系统状态吞掉事件。

## 已定论的坑（不要重新实验）

- **佩戴压感自动化不能用继电器**：继电器短接只能触发 INT 引脚，固件 `aw8687x` 靠力度值 `g_signal` 过滤事件，继电器伪造不了力度值（`g_signal` 恒 0 → `key_flag=0` → 无 action）。同机真人按压完全走通，证明根因在"伪造不了模拟量"而非固件逻辑。**最终方案改用固件测试指令** `SingleUsbShell.single_bud_key()`（`bud left/right sim key_single/double/triple`），继电器 R10/R11 吸合不能视为压感动作成功。给固件的精确需求是：测试模式下 `aw8687x` 驱动在 INT 触发时跳过 `g_signal` 阈值判断直接置 `key_flag=1`（已提交固件组，2026-07-16）。
- **红外可以模拟佩戴**：开盖+出盒前置下，R8/R9 短接保持=入耳（`hx300x` 去抖 5→1），断开=出耳（3→1）。但**佩戴检测长期被"5V 在位"误判屏蔽**：治具 Pogopin 即使切断触点，仍每隔几秒收到 `adp_5v_state: 1` 插拔脉冲，导致耳机自认在充电，固件直接丢弃佩戴变化事件（`in 5V, ignore ear status change`）——这是治具级根因，2026-07-16 改线后好转但仍偶发，断言要容忍重试。
- **Pogopin 串联常闭接法**：继电器吸合=切断触点=出盒，断开=入盒；出盒会真实切断耳机充电（佩戴检测因此解锁）。耳机在盒时 Pogopin 吸合无状态变化属正常，不是通道坏了。
- **机械继电器 50ms 脉冲偶发吞沿**（实测单击丢 1/2、双击丢 3/4、三击丢 4/6）——精确时序类自动化应换固态继电器或走固件测试命令，不要指望机械继电器打脉冲的时序稳定性。
- **压感手势时序规范**（人工确认）：一次点击=压感线 50ms 高 + 150ms 低 + 50ms 高；判定窗=最后一次点击后 500ms 静默；双击间隔 <500ms；长按 1s 切 ANC（计划改 2s）。手势断言必须走**对侧耳机**日志 `app_mmi_handle_action: action 0xNN`（remote_relay 中继，必现）——本侧耳机日志不可靠。动作码：单击=0x32、双击=0x34、三击=0x35。

## 日志锚点排查顺序（断言超时先查这个，不要一上来改正则）

命中率排序：**日志根本没在流动 > 锚点签名漂移 > 正则被 base64 分块截断 > 事件语义理解错**。

1. 先确认日志文件字节数在涨（DebugAnalyzer 的 `.log` 目录列表大小恒 0 是 NTFS 元数据假象，必须读内容判活）。耳机关盖深睡 UART 静默是**正常态**不是停流；输出文件在收到首字节时才创建。
2. 心跳门控：盒子无心跳约 5 秒后既不回命令也不推日志，`firmware_session` fixture 已常驻 1s 心跳，裸调试脚本要自己发心跳。
3. 宽过滤看全量再收敛关键词——多次"锚点不存在"其实是固件升级改了日志签名。
4. base64 跨块截断：盒子固件日志按 ~1KB 块上报，一行会跨块截断，所有日志正则必须在"原始流拼接"上匹配，不能逐块匹配。

**关键锚点速查表**：

| 事件 | 锚点 |
|---|---|
| 蓝牙连接 | `plaud_bud_connect_mode_status_change: ... 3`（3=已连接，side 0=左 1=右）；T0.2.22 前用 `SPP_CONN_CMPL`（已作废） |
| 开盖 | `[LID_REPORT] Lid: open`；结构化事件 `{'lid':{'status':'open/close'}}` |
| 佩戴/出入盒（免耳机 UART，走盒子日志） | `set bud_ext: primary_loc/secondary_loc`，loc 语义 1=在盒 2=出盒 3=佩戴 |
| 红外佩戴链（耳机日志） | `hx300x_int_debounce_handle`（in_ear 去抖 5→1 / out_ear 3→1）→ `hx300x_send_event_to_ui: action=1` |
| 震动 | `motor_no_start ...(action) steps=N` 锚定动作，数其后 `motor_no_play_block` 至 `last=1`（start_rec=1 次、stop_rec=2 次） |
| 手势动作码 | 对侧耳机 `app_mmi_handle_action: action 0x32/0x34/0x35`（单/双/三击） |
| WSS 上传完成 | T0.2.22 起从单行 `Upload complete: sent ...` 拆成 `[WSS] Upload complete: N bytes` + `Upload stats: sent ...`（断言已放宽兼容新旧） |

**已知断言坑**：

| 坑 | 正确写法 |
|---|---|
| 停录后固件查两次文件大小，第一次可能 `size=0` | 文件断言只认 `size=[1-9]\d*` |
| LED `recording_end` 仅关盖时上报（开盖时 LED 仲裁被盖况接管） | 停录权威事件 = `Business unrecord` |
| 配对键长按锁 LED pairing 场景 5 分钟（prio 90 > recording 50） | 期间 recording LED 断言必超时——录音用例别碰配对键，绑定与录音用例排班不要交叉 |
| LTE 在线时停录后文件自动 WSS 上传并删本地 | 文件断言有竞态：用 `DEV_RECORD_STOP_IND` file_size、停录后立即 LIST，或禁 LTE |
| 出入盒无结构化事件 | 用 earbud 状态查询 + `primary[left -> right]` 主从切换日志 |

## 环境噪声（归因时要排除，不要误判为响应）

- 左耳 `aw8687x` 每 5000ms 固定一跳 `timeout_cb: evt=3` + `g_signal: 0`——本底心跳，与激励无关；压感归因只认 `Force IRQ handler` 行。
- 治具接线导致 `adp_5v`/`excharger` 事件全程刷屏，无区分性。

## DebugAnalyzer headless 抓包（2026-07-17 打通）

`DebugAnalyzer.exe -j0 -fs -config "<角色>.ini"` 无 UI 自动开抓+实时解码，三实例（左耳/右耳/盒子）并发 OK。已产品化为 `root/reporting/debug_analyzer.py` + `debug_analyzer_autostart` session fixture，首个 hardware 用例前自动拉起，无需手动开客户端。关键事实：耳机用 sigma-tws bank1 trace，盒子用 sigma-charger；固件 OTA 换 bank 后解码变乱码需对调（ARM 用 bank1、DSP 用 bank0 是沿用手动客户端约定）；硬 kill 尾部丢失约 0-6 秒但会触发最终 flush，可接受。**固件升级只需改 `config.py` 的 `G_FIRMWARE_TRACE_ROOT` 一行**，镜像子目录和文件名自动发现最新。

## 固件升级后必做校准（每次 T0.2.x 升级都会破坏这几项）

1. trace 根目录时间戳必须与刷入设备的构建一致，不配则 UART 解码乱码。
2. 版本号：Allure 环境信息、固件 USB 日志版本目录段、UART 切片目录三个消费点都依赖它。
3. **固件升级会清 APP 侧绑定**（APP 设备列表变空，但盒子侧 `bind:True`/`ble:connect` 仍在——这是正常现象不是 bug），必须人工重新绑定；配对框不弹先去 iOS 设置>蓝牙>忽略此设备清残留。
4. 日志锚点可能整体漂移（见上表），复验方法＝宽过滤看全量。
5. 鉴权行为可能变化：T0.2.13 是未鉴权固件（`SECURITY_AUTH` 无响应，按 LEGACY 放行）；`SECURITY_AUTH` 响应 `seqNum` 与请求不一致是正常的，按 `cmdType`+游标匹配。

## 绑定/解绑（2026-07-23 移植自固件团队 JS 参考实现）

- 进配对态的复位手段=**继电器长按配对键 5 秒**，不是固件 reset 命令；配对态仅 5 分钟，必须"进扫描页那一刻"复位。副作用：配对键长按会锁 LED pairing 场景 5 分钟，绑定与录音用例不能交叉排班。
- **已知缺口**：解绑后未清理 iOS 设置>蓝牙"忽略此设备"，导致下轮绑定不弹配对框、报"耳机蓝牙未能完成配对"——尚未自动化。

## 端到端运行配方（首次双 PASS，2026-07-15）

1. 启动 Midscene 桥（仅 Android/AI 用例需要，iOS 已迁纯 WDA）。
2. `python -m pytest script/FN/test_fn_rec_box --env-config config/env.hardware.yaml --serial-port COM3 --phone-uuid <iOS UDID> --run-destructive`
3. `tools/generate_allure_report.bat` 生成报告（内置便携 JRE17，无系统依赖）。

APP 层判定口径：连接标志=首页顶部带电量标识的设备小图标+下拉箭头（无"已连接"文字）；录音中=列表出现无最终时长的条目（4.0.100(905) 起进行中图标从波形变省略号，需兼容双样式）；停录后条目消失（LTE 直传删本地），文件断言必须走固件 NOTES 日志/WSS 日志，APP 不留文件可查。

## 录音内容比对（2026-07-22 状态）

参考音频必须用**真实语音**而非纯音调——盒子 DSP 噪声抑制会把稳态音调压掉，越响压得越狠。频谱/包络比对对实验室背景噪声太敏感，已改为：`compare_audio` 只做时长覆盖率判据 + 读取 APP 云端转写文本与参考文本做字符级相似度比对（容忍 ASR 对数字/品牌名的合理误听）。
