没想到，今天就看到一位大佬（nekocode）分享了一个很棒的SKILL，名为 filetree\[1\]。

  

![[笔记同步助手/images/7dc97849ce189b9ad3903ec04c685b28_MD5.png]]

  

你看看这个filetree 的功能：会在每个项目里维护一份FILETREE.md 文件，里面包含：

-   完整的文件树
    
-   每个文件由 AI 生成的一句话描述
    
-   用于感知变更的hash（虽然但是我并不知道这个玩意儿，我觉得可以理解为一个 id 吧，但这并不妨碍我使用，欢迎留言区科普）。
    

在使用这个 filetree skill之前，我咨询过Antigravity：

![[笔记同步助手/images/801d2173abd4ed319a9940b06a07ce76_MD5.png]]

供大家参考

  

对于更技术层面的 SKILL 机制讲解，大家可以自己把这个 skill 丢给 AI 去看，我这里就不废话，也不想把 AI 的解释搬过来。

另外下面这 3 点，是我结合 filetree 的 README 和 AI 解读后，觉得比较值得关注的地方：：

-   它会通过静态扩展表（`SKIP_EXTENSIONS` 和 `SKIP_FILENAMES`）物理过滤掉 PNG、JPG、PDF、zip 等二进制静态资源以及 `package-lock.json` 等依赖锁文件，防止大模型将算力浪费在毫无摘要价值的文件上。
    
-   它有一个 `UNCHANGED` 增量缓存设计，在大项目在重构时，很多文件看起来被修改了，但其实只是调整了注释、修复了 Bug，或者改了格式，文件本身的用途并没有发生变化。
    

-   在更新时，大模型如果发现该文件的目的未变，可以直接输出 `UNCHANGED`。
    
-   在 apply 时，脚本会只更新物理哈希，而原位保留之前的摘要。这是一种很好的无状态缓存设计，对于大项目的更新会节约很多 Token成本。
    

-   它还能解决大中型项目目录树手工维护必过期的痛点，有了 `filetree`，开发团队只需要将该命令注册在 Git 提交流水线上（如 pre-commit 钩子，或是 CI 中的 `filetree:lint`），就能强制保障项目的结构与功能描述尽可能保持同步。
